### The enable command (coordinator, after the RAM upgrade)

```
ssh mike@10.0.0.30 'sudo bash ~/sandbox58/enable.sh --check'   # read-only: memory math + each server's state
ssh mike@10.0.0.30 'sudo bash ~/sandbox58/enable.sh'           # precheck, then enable + start, staggered
```

Precheck (exit 2, nothing changed): `MemAvailable >= PENDING x HEAP + 8 GiB`, HEAP = the `-Xmx` parsed from each unit
(2 GiB), PENDING = servers not yet active, so **16 GiB on a first run**; also refuses a missing dir/unit/jar, a
`server.properties` port other than the planned one, or a planned port with a listener. The same inequality is
re-checked before each start with the servers still to go. Then `daemon-reload`; per server `enable` + `start`, wait for
an RCON `list` reply (up to 600 s: first start generates the world), 12 s stagger; a server that never answers is
`disable --now`'d and the script exits 1 without starting the rest. Finally it reinstalls `/tmp/sbx-rcon.py` (gone after
the VM restart) and prints a table: active, enabled, ports, RSS, `list` reply, MemAvailable.

Verified on the real host without changing anything: `--check` today -> `REFUSED: MemAvailable 14.0 GiB < 16.0 GiB`
(exit 2); with a fake meminfo of 42.9 GiB -> `precheck OK`; at exactly 16 GiB -> OK, 1 kB under -> REFUSED; the
`MEMINFO` override refuses itself outside `--check`.

Ceilings: summed `MemoryHigh` (the throttle point) of all 24 units = 16 x 3 GiB + 8 x 2.44 GiB = **67.5 GiB < ~79 GiB**

its own cgroup, not the host. Right after the VM restart the fleet worlds have not grown back to 1.5 GiB yet, so
MemAvailable is temporarily ~6 GiB higher than steady state; the 16 GiB floor still holds at steady state (~40 GiB).
64 GB would fit at steady state (~24 GiB free) but leave the summed MemoryHigh (67.5) above MemTotal; 80 is the right size.

## 5. Per-server locks: how they coexist with the global lock

| lock (on 10.0.0.31) | holder has | taken by |
|---|---|---|
| `/tmp/mcai-sandbox.lock` (unchanged) | **every** sandbox | `sandbox/sbxlock.sh take all <tag> [note]`, or the old hand `mkdir` + `owner` |
| `/tmp/mcai-sandbox.lock.<name>` (new) | that one sandbox | `sandbox/sbxlock.sh take <name> <tag> [note]` |

`owner` first word = tag, as before. `sbxlock.sh` (works from the mini — it re-runs itself on .31 over ssh — or on .31)
also has `release <name|all> <tag>` (refuses another tag) and `status`. Only registry names are per-server lock names;
an ad-hoc dir like the `/tmp/mcai-sandbox.lock.stale-homefix-20261020` seen today is ignored.

**Taking is announce-then-check:** mkdir your own lock first, then look for the other kind (a per-server take looks for
the global lock; a global take for any per-server lock) and back out if present. Two concurrent takers can both back
out; they cannot both succeed (25-round race test). It never waits and never breaks a lock. Every take and release
runs inside a millisecond mutex (`/tmp/mcai-sandbox.lock-mutex`), so a release's "is this mine?" check and its `rmdir`
cannot interleave with another release or take (Codex r1 P1: two releases of one lock could otherwise delete the next
holder's). A mutex left by a killed run is reported (`MUTEX STUCK`, exit 3), never broken. Release refuses, touching nothing, a
lock dir that holds anything besides `owner` (Claude r1 P2: removing the owner and then failing the `rmdir` would leave an
ownerless dir that every driver and take reads as held — every sandbox wedged).

**Drivers enforce it** (`sandbox/lib/sbxlock.cjs` `requireSandboxLock(SERVER, tag)`, now called by all 13 lock-checking
drivers instead of each `cat`-ing the global owner file): a run on S is allowed only when **every lock covering S — the
global one and S's own — is absent or has this driver's tag as its owner's FIRST WORD, and at least one is held.** The
first word must equal the tag or be `tag-<label>` (`plinth-02 …` is a `plinth` holder). This is a tightening (Codex r1 P1):
the drivers used to regex the WHOLE owner text, so owner `plinth021 …` admitted the `plinth` driver and a note naming
another tag admitted that one. Drivers now pass exact tags (`'plinth'`, `['freeze', 'airpocket-02']`, stock's
`LOCK_OWNER`); a RegExp tag is refused. **Habit change:** an owner line must START with the driver's tag. A lock dir
without an owner file counts as held by someone else; a probe that prints anything but the two expected lines throws
(a silent probe is not "free"); an unreachable lock host throws (ssh error), never reads as free.
Tags are the only identity: two agents who both start their owner line with the same tag are indistinguishable to the
drivers, as before this change.

**Legacy coexistence, exactly:**
- A global holder with an unchanged workflow (hand `mkdir`, `bagbudget-paper.sh`, `kitshrink/lockwait.sh`) keeps working:
  every driver accepts the global lock naming its tag, as before.
- A hand `mkdir` of the global lock does not look for per-server locks. If someone holds S per-server at that moment,
  **every updated driver refuses on S for both of them** (loud, safe) while other servers stay usable for the global holder.
- **Residual gap:** an OLD copy of a driver (e.g. the trees under `~/bb03/` on .31) checks only the global lock, so it
  could run on sandbox..sandbox4 under someone's per-server lock. It cannot run on sandbox5..8 at all — its `PORTS` table
  does not know them. So: **per-server locks are fully safe on sandbox5..8 today; on sandbox..sandbox4 they are safe
  against drivers at or after this branch.** Prefer sandbox5..8 for per-server work until the old copies age out.
- **Most drivers check no lock at all** (pre-existing, but it matters more now): 27 of the 40 RCON-driving scripts
  under `sandbox/` never read any lock — `bamboo-ab`, `bamboo-abort-ab`, `bamboo-craft-ab`, `chest-ab`, `climbflood-ab`,
  `cobble-ab`, `cobble-cap-ab`, `composter-ab`, `craftroom-ab`, `craftsync`, `drive`, `foodskip-ab`, `grid-ab`,
  `orderroom-ab`, `peacefulkit-ab`, `pk-cursor-probe`, `realdrive`, `toolhygiene-ab`, `toolkit-ab`, `tools-ab`,
  `towndeposit-ab`, `trace-rot`, `withdraw-ab` (craft/), `well`, `well-e2e` (well/), `drown`, `tf-growth` — and neither do
  `run-scenario.sh`, `cl_world.sh` or a hand `sbx-rcon.py`. For all of these a lock, global or per-server, is a
  convention the agent keeps, not a guard. Only the 13 drivers listed in the test enforce it.
- **Hand releases** (`rm -rf /tmp/mcai-sandbox.lock`, the `rm owner && rmdir` in `bagbudget-paper.sh`) skip the
  mutex. They only touch the global lock, which `sbxlock.sh` never deletes for anyone else, so the release race above
  stays closed between `sbxlock.sh` users; a hand release racing an `sbxlock.sh take all` is the old, unguarded case.
- **Old driver copies** may also be standalone single files (e.g. `~/bb03/bamboo-abort-ab.cjs` on .31). A copy of one
  of the 13 updated drivers WITHOUT `sandbox/lib/` beside it fails at startup ("Cannot find module '../lib/sbxlock.cjs'"):
  loud, never open.
- `cl_run.py` (benchmark) now takes its server's per-server lock on .31 through `sbxlock.sh`, with one tag per process
  (`mbench-<pid>`); an ambiguous answer (ssh error, timeout, exit 0 without `TAKEN`) releases that tag before giving up,
  so a failed run cannot leak the lock nor release another run's (Claude r1 P2). **Bug found:** its old
  `sandbox_lock` did `os.mkdir('/tmp/mcai-sandbox.lock')` on the machine it runs on — the Mac mini — so it never excluded
  anyone; the shared lock is on .31.

Not changed (host copies the coordinator may sync): `~/monitor/lib/mcrcon.py` on .30 (`SANDBOX_WORLDS` still 1-4, so its
`assert_sandbox` refuses sandbox5..8), `~/bin/world-backup.sh` (comment only), `/tmp/sbx-rcon.py` (enable.sh installs it).
Six drivers listen on a fixed loopback brain port 11499, so two of them on ONE machine at once fail with EADDRINUSE
(loud); per-server parallelism with those needs different machines or the env overrides the newer drivers have.

"ANCHOR MISSING … drop the TOWN-PLACED.json filter" against today's `~/scripts/place-town.py` (fails identically at HEAD).
