**Why the 80% alarm said 90% when ES said 95%.** The old check computed `shutil.disk_usage().used / total`,
which leaves out root-reserved blocks. ES's watermarks count `(total - available) / total`. On 10-20
00:25Z the log said "90%", but ES had been at its 95% flood stage for an hour. The disk is the same
filesystem as `/` (the ES data volume is `/var/lib/docker/volumes/...`, and the snapshot repository
`/srv/es-backup` is on `/` as well). Over 09-23 -> 10-20 the series went 48% -> 91%, about 1.6 points a day
on the old ~100 GB disk.

## 1. The hole, per stream

A row is identified by its **canonical content**: the parsed JSON with null-valued keys dropped (filebeat
never ships them), integral floats as ints, sorted keys, then sha1. Files and ES are compared as a
**multiset** per (bot, hash), because legitimate byte-identical rows exist (154 in this window). ES was
walked in full with a point-in-time cursor, and the walk's count had to equal `_count`. The files were
walked in full: every rotated generation tagged >= 20261020, plus the live file read up to its size at open.

**Positive control: 22:00-23:00Z, the hour before the flood.** If the reader, the canonical form or the
matcher were wrong, this hour would show differences. It is exact.

| stream | files 22:00 | ES 22:00 | bot x 5-min buckets differing | ES docs with no file row (whole window) |
|---|---:|---:|---:|---:|
| skill | 58,521 | 58,521 | 0 of 960 | **0** |
| llm | 6,857 | 6,857 | 0 of 960 | **0** |

Every one of 138,465 skill and 15,828 llm ES docs in the window matched a file row by hash. So the
canonicalisation reproduces filebeat's shape exactly. Missing rows are not an artefact of it.

**The hole (before backfill).** Denominator: every row the files hold stamped in [23:00, 01:00).

| stream | files 23:00-01:00 | ES before | **missing** | 23:15-23:59 buckets | 00:00-00:04 bucket | bots affected | missing per bot (min / median / max) |
|---|---:|---:|---:|---:|---:|---:|---|
| skill (`mcai-skill-agents`) | 121,922 | 79,944 | **41,978** | 41,776 | 202 | 80 of 80 | 150 / 479 / 1,706 |
| llm (`mcai-llm-agents`) | 13,660 | 8,971 | **4,689** | 4,659 | 30 | 80 of 80 | 37 / 57 / 78 |
| Paper (`mcai-mc-paper`) | 16,813 lines on 10-19 + live | -- | **0** | -- | -- | 0 of 16 worlds | -- |

The 23:20-23:50 buckets hold **zero** ES docs for every bot. The 23:15 bucket is partial, at 4,077 of
4,821, and the hole starts at 23:16. The 23:55 bucket holds 12 skill and 9 llm docs. These are rows
stamped 23:55-23:59 that were written to the live file after the truncate, so filebeat shipped them
later. The 00:00 bucket loses 202 skill and 30 llm rows. This is the usual copytruncate race (~40-60
skill a day, per es-completeness-2026-10-14). It is larger here because the rotation happened under
backpressure.

**The hole is bounded.** 01:00-02:40Z is exact in both streams: skill 96,550 = 96,550 and llm 11,351 = 11,351,
with 0 buckets differing. After the block cleared, filebeat shipped everything still in the live files.

**Paper: no hole.** Paper's `@timestamp` in ES is filebeat's *read* time, so time buckets cannot be used.
The row key is (world, byte offset in `latest.log`, message after the pipeline's grok). Lines on an RCON
thread are excluded, because the `mcai-paper` pipeline drops them. Every rotated `2026-10-19-1.log.gz` and
every `latest.log` for the 16 shipped worlds was read on .30. **16,812 of 16,813** non-RCON lines were
found in ES. The one missing line was written in the minute of the check (live 03:00, hive-d), which is
ingest lag. That 16,812 is the positive control: the matcher finds presences. The likely reason
there was no hole: Paper writes ~500 lines an hour, which fits in filebeat's in-memory queue. Lines were
read on time (ES holds 529 docs stamped 23:xx), held in the queue, and delivered after 02:42. The ~60k-row/h
skill stream fills the same queue within minutes. That is consistent with the partial 23:15 bucket.

`mcai-sys-journal` (journald input, cursor-based, no rotation) was **not reconciled**. Its hourly counts
stay at 7.7k-8.0k through the window (23:00: 8,012). Absence of a dip is not proof.

## 2. The backfill

`infra/elk/flood-backfill.py`, run on .31 as `mike` under `nice 19 / ionice idle`.

- **Write credential.** This is the shipper account filebeat itself uses, read through `sudo -n cat
  /etc/filebeat/filebeat.yml` into memory. It is the same credential `infra/elk/llm-backfill.py` used.
  It was never printed, logged or put on a command line. No credential was created.
- **Exactly once, two ways.** First, the diff is recomputed from ES on every run. Second, each doc
  is sent as bulk `create` with a deterministic `_id` `fl261020-<sha1[:24]>-<k>`, where `k` is which
  occurrence of that row it is. A repeated send is a 409, not a duplicate.
- **Same document shape.** The filebeat config drops `agent/ecs/host/input/log` from skill/llm events and
  adds nothing else. The backfilled doc is the canonical row: nulls dropped, everything else as written.
  The 0-extras control above shows ES's own docs have exactly this shape.
- **Where they landed.** The current write indices are `.ds-mcai-skill-agents-2026.10.15-000011` and
  `.ds-mcai-llm-agents-2026.10.15-000011`. These are the same backing indices that were live at 23:00 (no
  rollover since).

## 4. `DiskLow`: seen days ahead, and somewhere it is read

`infra/backup/check-backup.py`, check 10. It still runs from the existing cron on .186:
`25 * * * * sudo -n /usr/bin/python3 /home/mike/check-backup.py >> /var/log/mcai-monitor/backup-alarm.log`.

- **The level.** `/` above **75%** used, counted ES's way, `(total - avail) / total`. The old
  `DiskPressure` checks now use the same definition.
- **The trend.** A least-squares fit of used **bytes** over 7 days, kept in
  `/var/lib/mcai-monitor/disk-history.json` (hourly samples, 8 days kept). The alarm fires if the fit
  projects crossing **85%**, ES's low watermark, within **14 days**. The fit uses bytes, not percent, so
  a disk grow does not read as a negative rate. It is a fit, not two endpoints, so one snapshot spike
  does not set it. With under 24 h or under 6 samples it says "growth rate not yet known" and gives the
  reason. It does not report a rate of zero.
- **Read where people look.** Each run writes its reading to ES index **`mcai-monitor-disk`**, one doc
  per host-hour. I created that index at install with 1 shard, **0 replicas** (a replica would turn the
  single node yellow) and `dynamic: false`. The check never auto-creates it. `fleetstatus.py` reads the
  newest doc with the read-only key and prints it as the second line of its report. Any `DiskLow` line
  is repeated there. The header also prints an alarm line in each of these cases:
  - the reading is missing;
  - the reading is **stale** (older than 2.5 h; in a flood stage the write itself fails, so staleness is the signal);
  - there is a **write block** on any shipped index (`_settings`, readable with `view_index_metadata`).
- **Why ES rather than ssh.** .31 has no access to .186, and the read-only key gets 403 on
  `_nodes/stats` and `_cat/allocation`. Giving .31 either access would mean a new key or credential, and
  that is the owner's decision.
- **No paging,** per the owner. These are report lines only.
