## 0. What it is

The 80-bot / 16-world bench stays the test bench. The showcase is ONE large, long-lived, peaceful world on its own
VM where 10 bots share one town for weeks: "build cool structures, survive, and work together". It runs only bench
builds that were promoted and then stayed inside the fleet build for 24 h (a lagging follower), on gemma4 26B on the
M4 Studio, with a qwen fallback **on the Studio, never on a bench GPU**. It is never drawn for a canary and cannot
enter a canary read, a draw, the tripper, or a fleet aggregate: nothing it writes lives where those read, and its ES
credential cannot write where they read (section 4). A 15-minute BlueMap timelapse records the town from the empty
world.

## 2. Brain routing

No bot-code change: the fleet's `LlmClient` takes `url|model` entries, logs the SERVED model and endpoint per row, and
with ONE endpoint retries it on every decision ("no alternative, will keep trying"). brain-01's `brain.mjs` was never
kept and is not used.

```
bot --http--> 127.0.0.1:11612 (VM) --ssh -L--> Studio 127.0.0.1:11502  showcaseproxy.py
     primary : LM Studio :1234 model `brain` (gemma-4-26b-a4b-it 8-bit, loaded by brain-01's keeper, KEEP_LOADED)
     fallback: the Studio's own Ollama :11434, qwen2.5:7b-instruct (the bench's own model, digest 845dbda0ea48, already on the Studio)
     paused  : 503 at once, no model called
```

* **Why not the 3090.** The Claude review measured (6 h to 12:3xZ) that .16 serves 24 % of bench decisions and is
  the PRIMARY for the 20 `*-d` bots, so the live canary arm (board-d + hive-a) is 50 % .16-first against 21 % of
  controls. Showcase load there would differ between arms. **No bench endpoint appears in any showcase env**, and the
  proxy never calls one. When the Studio is unreachable the showcase bots make no LLM decisions (reflexes still run).
* **`infra/showcase/showcaseproxy.py`** (new file; brain-01's `~/brain01/brainproxy.py`, plist, port 11501, tunnel
  and key are untouched). launchd `com.mcai.showcase.proxy`, KeepAlive:
  `--listen 127.0.0.1:11502 --upstream http://127.0.0.1:1234 --model brain --serve-as gemma4:26b
  --fallback http://127.0.0.1:11434 --fallback-model qwen2.5:7b-instruct --max-inflight 10 --timeout 20
  --fallback-timeout 20 --default-think false --log ~/showcase/proxy.jsonl
  --pause-file ~/mbench/out/GPU_RESERVED --pause-file ~/brain01/LIVE --pause-file ~/showcase/OFF
  --pause-dir ~/showcase/pause.d --quiesced-file ~/showcase/QUIESCED`.
  * **Paused means paused, by mechanism.** Any of these pauses the showcase (gemma AND the qwen fallback, same GPU):
    `~/mbench/out/GPU_RESERVED` (any holder: brain-01's keeper writes `brain01-live` during a brain canary; mbench's
    LM Studio runs and Stage C already hold it, and **this branch makes `bench/models/run_model.sh`'s Ollama and
    `serve` paths hold it too** -- they previously only waited for it), `~/brain01/LIVE`, the operator's
    `~/showcase/OFF`, any entry in `~/showcase/pause.d`, **or a running benchmark worker process**
    (`run_bench|throughput|serving|cl_run|cl_series .py`, found with `ps`, the proxy's own process excluded) for a
    benchmark started by hand.
  * **Acknowledged per reservation.** On a pause the proxy lets in-flight work finish (<= 40 s), waits a 30 s grace
    (an upstream generation it gave up on is bounded by max_tokens 512, well inside it), tells the Studio's Ollama to
    unload the fallback model it loaded (`keep_alive 0`), then writes `~/showcase/QUIESCED`. Any change in the set of
    pause sources withdraws the old acknowledgement and restarts the grace. `infra/showcase/studio-gpu-guard.sh`
    (`showcase_await_quiesced <reservation>`) waits for a QUIESCED newer than its own reservation and REFUSES after
    180 s with the remedy; run_model.sh and lms_factor.sh source it right after taking GPU_RESERVED. For a future
    brain canary (brain-02) the requirement is recorded, not built into the bench: its first read window starts > 1 min
    after LIVE (in-flight showcase work is bounded at 40 s + 30 s grace).
  * **A stale holder** (e.g. a Stage C `pause-*` left by a crash) would pause the showcase indefinitely: every
    heartbeat row carries the proxy's `/healthz` answer, and fleetstatus prints `SHOWCASE BRAIN PAUSED by <source>
    since <t> (N h)`.
  * `--default-think false`: the fleet code sends no `think`; brain-01 ran with thinking off.
  * `/healthz` is 200 only when not paused AND `brain` is loaded; the body names the pause file or the error.
  * Fallback fires on a primary error, timeout or LM Studio refusing; saturation of the showcase's own 10 slots
    answers 503 (the bot's next decision retries).
* **Timeouts, honestly.** Bot `LLM_TIMEOUT_MS` (fleet value, 45 s) per attempt, at most 2 attempts (one repair retry
  on invalid JSON); proxy primary 20 s + fallback 20 s < 45 s (the proxy refuses to start otherwise). A blackholed
  tunnel: ssh `ServerAliveInterval 10 x 3` drops it within 30 s, then connection refused is instant; a decision in
  flight then waits its 45 s. LM Studio holds 16 k context; the fleet asks `num_ctx 8192` (ignored by LM Studio, honoured
  by the Ollama fallback).
* **Tunnel** `showcase-studio-tunnel.service` (VM, user mike): `ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes
  -o ServerAliveInterval=10 -o ServerAliveCountMax=3 -o StrictHostKeyChecking=yes -i ~/.ssh/id_ed25519_showcase_tunnel
  -L 127.0.0.1:11612:127.0.0.1:11502 mike@ai.ticrcorp.com` (the Studio's public name, never its 192.168.19x address).
  Studio `authorized_keys` line, as brain-01's: `restrict,port-forwarding,permitopen="127.0.0.1:11502",
  permitlisten="127.0.0.1:1",command="/usr/bin/false" ssh-ed25519 ... showcase-tunnel`.
* **Capacity.** LM Studio `--parallel 12`; 10 bots at ~1 decision / 32 s x ~2 s = ~0.6 in flight on average.
* **Verification before any bot starts:** `replay-prompts.mjs` runs on the VM with the RELEASE's own `llm.mjs`
  (`LlmClient.decide`, `skillSchema`, `buildSystemPrompt`) against 127.0.0.1:11612 on 50 real bench user prompts that
  the feed ships (only WHOLE ones: under the logger's 6000-char cut and carrying their `saw_end` sentinel). The system
  prompt is rebuilt from the release and its hash compared with each row's `system_hash` (the positive control that the
  replay sends what the bench sent; a mismatch is reported, not hidden). Pass: `schema_valid` with the matching sentinel
  on >= 48 of 50 and served model `gemma4:26b` on all. A second pass with `~/showcase/OFF` present must get 503s; a
  drill proxy instance on another port with a dead primary must be served by `qwen2.5:7b-instruct`.

## 3. Deploy / follow policy — a lagging follower

**Source of truth: the bench's own records, through a one-command feed.** `.31:~/showcase-feed.py` (new, read-only)
prints one JSON document: the trial manifest; EVERY journal row whose phase is `promoted`, `owner-direct`, `recorded`,
`poll-revert`, `contained` or `torn-down` (the whole journal, filtered: KEEPs never age out); a census (each bench
bot's newest skill row: bot, ts, `code.version`); md5s of .31's `package-lock.json` and `node_modules/.package-lock.json`;
and ONE control env (a `board-*` bot outside every declared canary pool whose newest row reports the majority control
build). The VM's key is in .31 `~mike/.ssh/authorized_keys` as
`restrict,from="10.0.0.40",command="/usr/bin/python3 /home/mike/showcase-feed.py" ... showcase-feed` (the forced
command ignores whatever the client asks to run). No ES key on the VM; no write path to the bench.

**The rule** (`infra/showcase/followrule.py`, pure, tested). The follower observes the feed hourly and keeps its own
ledger (`/srv/showcase/follow-ledger.jsonl`):
* an observation is **VERIFIED** only if the census covers >= 85 % of the expected non-canary roster (the env-file
  roster minus declared canary pools) with a row in the last 30 min, and >= 90 % of those report ONE `code.version`
  whose sha part equals `declared_code_version` (the manifest alone is a claim);
* an unverified observation is **EXPLAINED** -- neutral, it neither counts nor breaks the run -- when a deploy in
  progress accounts for it: the manifest was declared < 45 min ago, or every off-majority bot reports the previous
  verified version or the canary build (a promotion restarts 80 bots over ~16 min; a teardown clears `canary_pool`
  before its restart step);
* the **unbroken run** is the newest stretch with one policy digest and one dependency digest, no gap > 2.5 h, in
  which two CONSECUTIVE unexplained unverified observations end it;
* the target is **the newest promoted sha P** (a hex in a `promoted` note, resolved by a unique prefix) that is an
  ancestor-or-equal of the declared sha in every verified observation covering the last 24 h of an unbroken run that
  reaches back 24 h -- a lagging pointer, so frequent promotions do not starve it (F itself was stable 24 h only three
  times between 10-11 and 10-20);
* **DUE** iff the target differs from the showcase sha;
* **ROLLBACK** iff the showcase sha S is no longer an ancestor-or-equal of the newest verified F, or contains a sha the
  operator listed in `/srv/showcase/REVOKED` (a bench revert made as a FORWARD commit keeps ancestry, so it must be
  named). The rollback target must itself pass the 24 h containment test; else the newest promoted common ancestor of
  S and F; **if neither exists: STOP** -- `stop-bots.sh`, nothing admissible runs;
* **HOLD** (fail closed) on a missing/failed feed, an unparseable manifest, an unexplained unverified newest
  observation, or no eligible P; every HOLD prints its reason and, when only time is missing, when it becomes DUE;
* the REQUIRED_KEPT town-plan pieces (section 9) are re-checked on **every** deploy, not only at the first start; a
  release missing one is refused (and a running showcase that would lose one STOPs instead).
* Owner-direct rollouts (whose journal rows carry no sha) are followed only as ancestors of a later promoted sha --
  which they always are, since a promotion is built on the fleet build. **D5: the owner is asked to confirm that
  owner-direct changes count as "kept" for the showcase** (fleet 9e7d9980 contains adbec4f4 and 469cba5a, both
  owner-direct).

**Executing it.** `showcase-follow.py` (systemd timer, hourly, under `ops.lock`) appends one ledger row and one decision
row (`/srv/showcase/follow.jsonl`). Only when `/srv/showcase/AUTO_FOLLOW` exists does a DUE/ROLLBACK/STOP act; it
can also be run by hand. `showcase-deploy.py` has two halves:
* **stage** (`--stage <sha>`; never touches a bot): `git archive` of `bots/` at the sha into
  `releases/<sha8>-<policy8>-<deps8>/src`; `node_modules` from an immutable artifact
  `/srv/showcase/artifacts/node_modules-<deps digest>.tar.zst` -- captured from .31's installed tree (a read-only
  rrsync key whose root is exactly `/srv/mcbots/harness/node_modules/`) only when .31's digest equals the digest the
  unbroken run observed, and checked against that digest after unpacking (fleet deploys never run `npm ci`; .31's
  lock differs from the repo's); envs from the run's pinned control env; the expected `code.version` =
  `<sha>+<srcDigest>` computed with config.mjs's own algorithm (sha256 over the sorted top-level `src/*.mjs` names +
  bytes, 6 hex) and written to `RELEASE.json`;
* **activate** (`--activate <release>`): switch the symlink; if bots are running, restart them **12 s apart** and verify
  within 10 min that **all ten** bot names have a skill row newer than their restart with exactly the expected
  `code.version`; else switch back, restart again, write `ROLLBACK` to `/srv/showcase/deploy.jsonl`, remove
  `AUTO_FOLLOW`. With no bots running (the state today) activate only switches the symlink; the ten-bot verification
  happens in `start-bots.sh`.
The first release is staged by hand before the 24 h ledger exists: `showcase-deploy.py --stage <sha> --bootstrap`
accepts only a promoted sha that is inside the CURRENT verified fleet build, and marks the release `bootstrap`
(follow.jsonl records it); the bots stay stopped, and the first DUE replaces it.

## 4. Exclusion from the tripper, manifest, draws, reads, fleetstatus, goalboard

Three independent mechanisms.

1. **Nothing on the bench hosts that a bench script enumerates.** No showcase unit, log, state dir or env file on .31;

## 6. Timelapse: every 15 min, from frame 0

**On the showcase VM, not .30.** The coordinator's note points at .30's `~/bluemap`; a 15-minute render needs the
world's region files, which on .30 means 96 world mirrors a day onto a host with 13 GB available and 16 Paper servers.
On the VM it is local. It reuses .30's proven pieces: the same BlueMap CLI jar (sha256 `7940d561...`, Java 21), the
same `capture.mjs` (puppeteer + SwiftShader, UI hidden, fov pinned), `tl.py`'s snapshot-then-render method and
`min_free_gb` guard, and `tl_assemble.sh`'s stamp. The owner's live map is `http://10.0.0.40:8100`
(`showcase-bluemap-web.service`, nice 19, reading the same rendered tiles). D1 asks the owner to accept the location.

* **Map:** `showcase`, render-mask home ±384 for the timelapse map (the live map's mask is the same; raised later for
  expeditions), `sky-light 1`, `ambient-light 0.1` (fixed lighting: no day/night flicker), file storage.
* **Every `CAPTURE_MIN` (15; `/srv/showcase/timelapse/tl.conf` and the timer, which must agree — the status line
  warns if not)**, `showcase-tl.service` (`TimeoutStartSec=13min`, `Nice=19`, `IOSchedulingClass=idle`,
  `CPUQuota=200%`) runs `tl_showcase.py capture` under `flock -n`:
  1. **free-disk guard** (< 20 GB free: an `ok:false` row, nothing written);
  2. **snapshot**: RCON `save-off` + `save-all flush` (the showcase world is ours; this is a save pause, not a world
     edit), a local `rsync` of the region files that intersect the mask plus `level.dat` into a persistent mirror
     (`timelapse/mirror/world`), then `save-on` (always, in a `finally`) -- a consistent copy, and BlueMap never reads a
     file Paper is writing (the CLI's incremental `-r` renders only chunks whose stored modification time moved, per
     BlueMap's docs);
  3. `nice ionice java -Xmx3G -jar bluemap-cli.jar -c <cfg> -r -m showcase` — **incremental, never `-f`** (one full
     render happens once, before frame 0);
  4. one puppeteer run, two frames into a staging dir: **topdown** = flat orthographic view centred on home spanning
     ~192 x 192 blocks; **angled** = a fixed perspective camera hash. **Both are published together or not at all**, and
     each must be >= 20 kB AND show terrain: in a 320 x 180 grayscale reduction, >= 30 % of pixels must differ from
     the frame's most common value by > 12 levels (a sky-only or half-loaded frame fails); the pair is judged by the
     reader too -- videos and the missing count use only stamps present in BOTH views;
  5. one heartbeat row (`ok`, failed step, render s, render CPU-s from rusage, capture s, bytes, disk free GB).
  A failed step is a row with `ok:false` and no frame — never a crash, never a retry storm; the next slot tries again.
* **Missing frames are counted from outside the job** (`scripts/lib/showcasestatus.py`): expected = the 15-min slots
  since `max(24 h ago, frame 0)`, present = slots with an ok regular (non-event) heartbeat in ES. A killed or never-run
  job therefore reads as missing slots, not as zero. fleetstatus prints
  `SHOWCASE TIMELAPSE <OK|GAPS|STALE|NO HEARTBEAT>: newest frame N min ago; last 24 h: a of b slots captured (m missing),
  f failed runs, s overrun skips; median X CPU-s per capture; every 15 min`.
* **Frame 0** is captured on the empty pregenerated world before the town is stamped and before any bot joins
  (`FRAME0.json` names it and the world's seed / level.dat hash).
* **Storage:** every frame kept. Measured on .30, frames average ~1.9 MB, so 2 views x 96/day = **~365 MB/day,
  ~11 GB/month**; the 320 GB disk holds > 2 years; the NAS (42 TB free) holds all of it.
* **Videos** (`tl_video.py`, systemd timers, nice/ionice, libx264 crf 20, **10 fps**, UTC stamp burned in after dedup):
  daily 00:20Z (every frame of the previous UTC day), weekly Mon 00:40Z and whole-history daily 01:00Z (one frame
  per hour: the first regular frame inside each hour bucket), monthly on the 1st 01:20Z (one per 4 h; skipped for a
  month with no frames). **No-change frames are skipped in the video only**: downscaled 320 x 180 grayscale, compared
  with the last INCLUDED frame, dropped when < 0.2 % of pixels moved by > 12 levels; first and last always kept; the
  count goes in the video's `.json` sidecar.
* **Event frames** (`capture --event <label>`, same pipeline, suffix `-event-<label>`, never fill a slot): the hook
  exists; wiring it to a plinth-complete / plot-built row is a follow-up.
* **Cost** is measured: the build reports the full render's CPU-s and the median incremental capture's CPU-s; if the
  median exceeds 60 CPU-s the report says so and the owner decides.

## 7. World and site

For up to 4 candidate seeds the server generates the world and `infra/showcase/site_search.py` (it imports
place-town.py's probes — `column()`, `surface_y()`, `matches()` with the tri-state Probe, so an unloaded chunk RAISES,
never reads as flat dry land — and writes no blocks) scores candidates on a spiral from spawn (step 96, rings 0-3) for
the town plan's **128 x 128** footprint: a 17 x 17 grid; the central 64 x 64 core dry with relief <= 4; area wet <= 3 %,
relief p90-p10 <= 8, canopy <= 30 %; wood on rings 80-128 (>= 8 of 48); water 96-256 blocks out (well at the edge,
farm water); spawn distance as a tie-break; a positive control per candidate (sky reads air; a counted solid column
re-reads solid). The best seed+site wins; the losing worlds are deleted. Gamerules = the bench's. Peaceful. Border
5000 on home. Pregenerated radius 1024 (`infra/showcase/pregen.py`: place-town / pregen-world imported with their
`ROOT`/`ARMS`/`BASE_RCON` overridden for this one world; no bench script edited).
**The town is NOT stamped now** (frame 0 is the empty world). The stamp — or the town plan's own first build — is a
step of `start-bots.sh`, idempotent (it refuses if `TOWN-PLACED.json` exists) and tied to FRAME0's world identity.
The site note `docs/reports/showcase-site-2026-10-20.md` records the seed, home, plot area and the siting-file fields
expected from the town plan.
