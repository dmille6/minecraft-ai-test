## 0. What it is, in one paragraph

The 80-bot / 16-world bench stays the test bench. The showcase is ONE large, long-lived, peaceful world on its own
VM where ~10 bots share one town and play for weeks: "build cool structures, survive, and work together". It runs
only bench builds that were KEPT and promoted and then stayed the fleet sha for 24 h (a lagging follower), on the
best brain (gemma4 26B on the M4 Studio) with qwen2.5:7b on the 3090 as fallback. It is never drawn for a canary,
and it cannot enter a canary read, a draw, the tripper, or a fleet aggregate, because nothing it writes lives where
those read (section 5). A 15-minute BlueMap timelapse records the town growing from the empty world.

## 2. Brain routing

**No bot-code change is needed.** brain-01's `brain.mjs` (`OLLAMA_BRAIN_PRIMARY`) was never KEPT, so the showcase
cannot run it; but the fleet's `LlmClient` already accepts a per-endpoint model (`url|model`), walks the pool in
order, cools a failing endpoint down (60 s doubling to 900 s) and logs the SERVED model and endpoint on every row.

```
bot -> 127.0.0.1:11612 (showcase VM) --ssh -L--> Studio 127.0.0.1:11502 (showcase proxy) -> LM Studio :1234 model "brain"
    \-> fallback 10.0.0.16:11434 qwen2.5:7b-instruct (the 3090; ollama-3090 VM 200)
```

* **Studio, a SECOND proxy instance** `com.mcai.showcase.proxy` (launchd, KeepAlive) runs `~/showcase/brainproxy.py`
  (a copy of brain-01's proxy with two added, default-off options, file in `infra/showcase/brainproxy.py`):
  `--listen 127.0.0.1:11502 --upstream http://127.0.0.1:1234 --model brain --serve-as gemma4:26b --max-inflight 10
  --log ~/showcase/proxy.jsonl --default-think false --yield-file ~/brain01/LIVE --off-file ~/showcase/OFF`.
  brain-01's proxy (:11501), its plist, its tunnel on .31 and its key are **not touched**.
  * `--default-think false`: the fleet code sends no `think`; brain-01 measured with thinking off, so the showcase
    proxy sets `enable_thinking: false` when a request carries none (tested 12:3xZ: the model returns 0 reasoning
    tokens either way today; the flag pins it).
  * `--yield-file ~/brain01/LIVE`: while a brain canary is live (its keeper flag), the showcase proxy answers 503 at
    once, so showcase bots fall back to qwen and the canary's Studio conditions match brain-01's measurement (the
    canary's p95 latency gate would otherwise see 20 bots on a 12-slot model). `~/showcase/SHARE` (present) disables
    the yield — owner switch, default absent.
  * `--off-file ~/showcase/OFF`: manual pause of the showcase brain (503 always).
* **Tunnel** `showcase-studio-tunnel.service` on the VM: `ssh -N -L 127.0.0.1:11612:127.0.0.1:11502` with a NEW key
  `id_ed25519_showcase`, restricted on the Studio exactly like brain-01's:
  `restrict,port-forwarding,permitopen="127.0.0.1:11502",permitlisten="127.0.0.1:1",command="/usr/bin/false"`.
  A dead tunnel = connection refused = immediate fallback; systemd restarts it in 5 s.
* **KEEP_LOADED** already exists (the keeper keeps `brain` loaded). The showcase does **not** hold `GPU_RESERVED`.
* **Interaction with the bench's GPU_RESERVED queue (`~/mbench`):** that queue waits only for `GPU_RESERVED`; the
  showcase never writes it, so model benchmarks are not blocked. But an mbench `serve-lms` line runs
  `lms unload --all; lms server stop`, which removes the showcase's model (and the keeper reloads it within a minute
  unless `~/brain01/PAUSE` exists). During that window the showcase runs on qwen. Operator rule, written into the
  Studio README: before an mbench LM Studio run, `touch ~/showcase/OFF` (clean fallback, no 502 storm) and
  `touch ~/brain01/PAUSE`; remove both after. A benchmark run with the showcase on the Studio would measure under load —
  the OFF file prevents that.
* **Capacity.** LM Studio loads `brain` with `--parallel 12`; brain-01 served 10 bots at p95 4.75 s. 10 showcase bots
  at one decision per ~32 s x ~2 s = ~0.6 requests in flight on average; the proxy fails fast at 10 in flight.
* **Fallback cost on the bench.** All 80 bench bots list `10.0.0.72` first and `10.0.0.16` second. The showcase uses
  .16 only while the Studio is down, OFF, or yielding: +10 bots on the bench's fallback GPU. Both canary arms carry
  pools on both GPUs (the draw records halves), so the shift is common to both arms of a DiD; it is still a load change,
  so every showcase llm row records `llm.endpoint` and fleetstatus' showcase line prints the fallback share for 3 h,
  which is the readable record of WHEN it happened.

## 3. Deploy / follow policy — a lagging follower of KEPT builds

**Source of truth: the bench's own manifest and journal, read through a one-command feed.** `.31:~/showcase-feed.sh`
(new, read-only, ~20 lines) prints one JSON object: the trial manifest, the last 600 journal rows, and one CONTROL
bot's env file (the first `board-*` bot not in `canary_pool`). The VM's key `id_ed25519_showcase_feed` is in .31
`~mike/.ssh/authorized_keys` as `restrict,command="/home/mike/showcase-feed.sh"` — it can run that and nothing else.
No ES key on the VM, no write path back to the bench.

**The rule** (`infra/showcase/followrule.py`, a pure function with tests):
* fleet sha `F` = `manifest.declared_code_version` (the control build; a canary only sets `canary_code_version`);
* `changed_at(F)` = the later of (a) the newest journal row with phase `promoted` or `owner-direct`, and (b) the first
  time the follower itself saw `F` (its own log, `/srv/showcase/follow-seen.jsonl`);
* **DUE** iff `F != showcase_sha`, `now - changed_at >= HOLD_H` (**24 h**), `F` is fetchable from origin, and the
  newest journal row is not a `poll-revert`/`contained` of a run whose sha is `F`. Otherwise HOLD (with the reason) or
  NOOP. 24 h on 80 bots = ~1,900 bot-h of fleet exposure before the showcase sees a build.
* A ROLLBACK on the bench (F becomes an ancestor of the showcase sha) is DUE immediately (no hold): the bench backed
  out of something the showcase is running.

**Executing it.** `showcase-follow.py` runs hourly (systemd timer). It writes its decision to
`/srv/showcase/follow.jsonl` every run. When `AUTO_FOLLOW` exists (`/srv/showcase/AUTO_FOLLOW`, created by
`start-bots.sh`) a DUE decision runs `showcase-deploy.sh <sha>`; without it the decision is only recorded.
`showcase-deploy.sh` (refuses any sha the rule does not call DUE, except `--preview`, section 9):
`git fetch`, `git checkout --detach <sha>`, rsync `bots/src` -> `harness/src`, `npm ci` only if the lock file changed,
rebuild the env files with the CURRENT control env, then (if bots are running) restart them **12 s apart**, then verify:
within 10 min every running bot's newest skill row carries `code.version == sha` (positive control: the row count is
printed), else it rolls back to the previous sha the same way and writes `ROLLBACK` to the deploy journal.

## 6. Timelapse (owner 12:55Z + 13:10Z/13:15Z): every 15 min, from frame 0

**Where it runs: on the showcase VM, not .30.** The coordinator's note points at .30's `~/bluemap`; this design puts
BlueMap next to the world instead, and says why: a 15-minute incremental render needs the live region files — on .30
that means a 96-per-day network mirror of the world onto a host with 13 GB available and 16 Paper servers pinned to all
32 cores. On the VM the render reads its own disk at nice 19 / ionice idle. It reuses .30's proven pieces unchanged in
spirit: the same BlueMap CLI jar (sha256 `7940d561...`, Java 21), the same `capture.mjs` (puppeteer + SwiftShader,
UI hidden, fov pinned), the same map-conf style and `tl_assemble.sh`'s drawtext stamp. The owner views the live map at
`http://10.0.0.40:8100` (a persistent `showcase-bluemap-web.service`, nice 19) — the same viewer, one link per world.

* **Map:** `showcase` map, render-mask home ±768 (raised later for expeditions), `sky-light 1`, `ambient-light 0.1`
  fixed (static lighting: no day/night flicker, which is why renders and not an in-game camera), file storage.
* **Every `CAPTURE_MIN` (default 15; one config line in `/srv/showcase/timelapse/tl.conf`)** a systemd timer runs
  `tl-showcase.py capture` under `flock -n` (an overrunning capture is skipped, never stacked):
  1. `nice -n 19 ionice -c3 java -jar bluemap-cli.jar -c <cfg> -r -m showcase` — **incremental** (never `-f`): only
     chunks modified since the last render. Timeout 10 min.
  2. one puppeteer run, two frames from fixed URLs against the persistent webserver:
     **topdown** = flat (orthographic) view centred on home, zoom set so the frame spans ~192 x 192 blocks
     (the viewer composes it from the rendered tiles); **angled** = perspective view, fixed camera hash
     (`map:x:y:z:distance:rotation:angle:tilt:ortho:mode`) from `tl.conf`, so the town grows in place.
  3. files `/srv/showcase/timelapse/frames/{topdown,angled}/YYYYmmddTHHMMZ.png`; **every frame is kept**.
  4. one heartbeat row to `/var/log/showcase/heartbeat.jsonl`: `ok`, failed step, render s, render CPU s
     (from `/proc` rusage of the child), capture s, bytes, frames in 24 h, **missing in 24 h** (expected
     `1440/CAPTURE_MIN` minus present). **A failed render or capture is a row with `ok:false` and no frame — never
     a crash, never a retry storm.**
* **Frame 0** is captured on the empty pregenerated world before the town is stamped and before any bot joins
  (`frames/*/<stamp>.png` + `FRAME0.json` naming it).
* **Videos** (`tl-video.py`, systemd timers, nice/ionice, ffmpeg libx264 crf 20, ~10 fps, UTC stamp burned in):
  * daily 00:20Z: every frame of the previous UTC day, per view;
  * weekly (Mon 00:40Z) and whole-history (daily 01:00Z): one frame per hour (the first frame at or after hh:00);
  * monthly (1st, 01:20Z): one frame per 4 h — produced once a month of frames exists;
  * **no-change frames are skipped in the video only**: a frame whose downscaled (320 x 180, grayscale) pixels differ
    from the last INCLUDED frame by > 12 levels on fewer than 0.2 % of pixels is dropped from that video; the count is
    written to the video's `.json` sidecar and the heartbeat. Storage is never pruned.
  * output `/srv/showcase/timelapse/video/{daily,weekly,monthly}/...mp4`, `history-{view}.mp4`.
* **Event frames (optional, cheap):** `tl-showcase.py capture --event <label>` is the same capture with a suffix;
  a follow-up can call it from a log watch on a plinth-complete / plot-built row. Not wired now.
* **NAS:** a daily job on .30 (section 8) pulls `/srv/showcase/timelapse/` and rsyncs it to
  `/volume1/homes/mike/showcase-timelapse/` with .30's existing NAS key, then checks the NAS file count. Expected
  ~100-200 MB/day of PNGs (2 x 96 frames); the NAS has 42 TB free.
* **Cost** is measured, not assumed: the heartbeat's render CPU s per capture, reported in the build verification.
  If a 15-min capture costs more than 60 CPU-s median, the report says so and the owner decides.

## 7. World and site

Fresh seed, chosen by measurement. For up to 6 candidate seeds the server generates the world and
`infra/showcase/site-search.py` (it imports place-town.py's probes — `column()`, `wood_nearby()`, the wet-biome rule —
and writes nothing but the probe armor stands) scores sites in an outward spiral from spawn on a **128 x 128 block
candidate plot area**: sampled every 8 blocks (289 columns), relief of the solid ground, wet fraction, canopy
fraction, wood hits in a ring 70-120 blocks out, and a river/lake within 250 blocks (water for the well and farms at
the edge, never under the plots). The best seed+site wins; losing worlds are deleted before the chosen one is
pregenerated. Gamerules = the bench's (`keepInventory`, no weather cycle, immediate respawn, no fire tick, no mob
griefing). Peaceful. Border 5000 centred on home. **The town is NOT stamped yet** (frame 0 is the empty world); the
stamp (deposit chests, beds for 10, lectern, as place-town but sized for 10) or the town plan's own layout is a step
of `start-bots.sh`. The site note `docs/reports/showcase-site-2026-10-20.md` records the seed, home, plot area and the
siting-file fields this design expects from the town plan.

## 9. Bot start gate, preview switch

**The bots do not start now.** `/srv/showcase/bin/start-bots.sh` is the ready command; it refuses unless ALL hold:
1. `/srv/showcase/REQUIRED_KEPT` lists the town plan's first pieces by run id (the per-town siting file, sorted
   deposits, station placement into plots), and for each the journal (via the feed) has `recorded KEEP` and the
   showcase sha descends from its sha (`git merge-base --is-ancestor`). An empty/missing file refuses.
2. the showcase sha is what the follow rule calls current (24 h stable on the fleet) — or `--preview` (below).
3. `/srv/showcase/town-site.json` (the town plan's siting file, section 7 fields) exists and validates.
4. the town is stamped (or the town plan declares it builds its own core) and FRAME0.json exists.
5. the brain path answers: tunnel up and the proxy `/healthz` 200 (else refuses without `--allow-fallback`).
6. filebeat active; the four showcase streams writable (a positive-control doc count).
Then it rebuilds the env files, enables + starts `mcshow@showcase-<Name>` **12 s apart**, creates `AUTO_FOLLOW`, and
verifies: 10 joins in the Paper log, each bot's first llm row, and the served-model share.
`stop-bots.sh` stops them 12 s apart and removes `AUTO_FOLLOW`.

**Preview switch (designed, OFF by default, recommendation: keep it off).** `showcase-deploy.sh --preview <sha>`
deploys a non-kept sha only if `/srv/showcase/PREVIEW_ENABLED` exists (created by a human with an owner note inside);
rows then carry `EXP_BLOCK=showcase-preview` and `RUN_ID=showcase-preview-<sha8>`, auto-follow pauses, and the next
DUE kept sha ends the preview. Off by default because the owner's rule is that the showcase runs only kept builds.
