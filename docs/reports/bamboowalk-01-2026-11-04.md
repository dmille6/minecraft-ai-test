## 2. Mechanism (verified on Paper, s.5)

minecraft-data 1.21.8 gives every bamboo state one collision box, `[0.15625,0,0.15625,0.34375,1,0.34375]`: the vanilla post
(6.5..9.5/16) moved by the XZ offset of block (0,0), which is (-0.25,-0.25). Vanilla moves each post by its own block's offset
(offsetType XZ, `Mth.getSeed(x,0,z)`, +-0.25). So mineflayer's physics walks into posts the server has and stops at posts it
does not; Paper teleports a body whose new box meets something new back where it was. The pathfinder's own straight-line
shortcut simulates with the same wrong boxes. cornerwalk-01's diagonal rule does not help: the cells are right, the boxes are
not. Upstream: prismarine-block #125 (2026-10-03) added the offset to INTERACTION shapes and left collision as it was; no
issue in mineflayer, mineflayer-pathfinder (#29, #157, #223, #310 are the generic shape/corner reports) or prismarine-physics;
Geyser documents the same rubber-band class for bamboo on Bedrock.

## 3. The change

`bamboowalk.mjs`: a mineflayer plugin wraps `bot.blockAt` once (loaded right after createBot, so it runs after mineflayer's
own blocks plugin defines it; physics and the pathfinder look `bot.blockAt` up on every call). A returned `bamboo` gets fresh
`shapes` moved from the baked offset to its true one: y unchanged (pathfinder heights, every full-cube test), the registry's
arrays never written, never throws, non-bamboo returns at one lookup. Bamboo only (pointed_dripstone has the same baked
offset and is left for later). `_bamboowalk_mode` licence row once per spawn (`wrapped=1` is the witness).
