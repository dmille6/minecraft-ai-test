VERDICT: CHANGE

1. **P1 — §5 F0–F3; §9: founding does not follow from these redirects.** With no chest, `deposit` returns failure before recovery (`bots/src/skills.mjs:2734`); automatic deposit requires an existing container (`bots/src/towndeposit.mjs:278`). F1’s lighting order is absent from §7.1. Pads may require fill, but no early piece builds it. Add deterministic survey, foundation and first-container orders, with explicit materials, triggers and restart behavior; prove founding from zero infrastructure before starting showcase bots.

2. **P1 — §§4.3, 6.1, 7.2: the required inventory index does not exist.** `cobbleObserve` records `stockCounts` (`skills.mjs:3291`), whose targeted groups exclude iron, copper and coal (`stocktarget.mjs:53`). It cannot select metal/fuel homes or find arbitrary item holders. Move the prior design’s §3.3a counting extension ahead of these readers; define per-item counts, freshness, components, canonical double-chest identity and unknown handling without adding disposal targets.

3. **P1 — §7.2: top-up is not predictable from item name and count.** The existing implementation deliberately uses empty slots because differing components can cause swaps (`towndeposit.mjs:200`). Moreover, `verifyTown` requires destination count equal to the transferred stack (`skills.mjs:7148`), which fails after merging. Specify component-compatible merging, reserved remainder capacity, server-confirmed cursor recovery, partial-transfer accounting and revised verification. Paper must exercise incompatible components, concurrent changes, interruption and no remaining empty slot.

4. **P1 — §§7.3, 8 T2–T3: tidy can strand or dispose of stock.** Town deposit keeps all iron/coal and stockpile reserves (`towndeposit.mjs:110`, `:118`), requires a near-full bag, and respects withdraw holds. Therefore “not kept by any keep rule” is false. Ordinary deposit also cannot reliably return relocated stock above a cap. Add persistent carry notes and a deterministic return order independent of bag fullness, with relocation-specific claims, destination reservation, allowance accounting and restart reconciliation. Test cap refusal and interruption together.

5. **P1 — §§6.1, 7.2–7.3: destination priority preserves scatter.** Step 1 prefers any existing holder—including drain chests—over the designated home. Tidy then uses that same order and can return stock to its source or another drain. Prefer designated compatible homes; exclude the source and drain destinations during tidy. Define progress as increased stock in designated homes or verified slots freed, not merely depositing into an existing holder.

6. **P1 — §§4.1, 4.5, 9: publication is not a complete reservation protocol.** Exclusive `link()` creation does not prevent a stale writer publishing N+2 without N+1’s claim. “Newest generation” and “lower generation wins” need explicit cumulative-history semantics. Specify world-keyed siting leases, predecessor validation/retry, fencing before mutation, immutable built reservations and abandonment. Reconcile `townplan` with the prior `townsites` protocol and require floor/plinth/placement adopters before inner-domain construction. Provide executable survey/re-site outcomes, not merely “next generation.”

7. **P1 — §§3, 7.1, 7.4, 8 B1–B3: the chest-first building needs its own proof.** Recovery currently rejects adjacent chests (`chestfull.mjs:478`), conflicting with the proposed contiguous row. The earlier storehouse required roof-before-containers to preserve sight lines. Specify permitted pairing, canonical group ownership, construction stands and yield geometry with founding chests present. Never journal a newly placed container as EMPTY by assumption: open and observe its actual combined inventory, including adoption, races and crash recovery.

8. **P2 — §1.2: correct the search descriptions.** Model `withdraw` uses `withdrawSweep` and at most three visits (`skills.mjs:10253`, `:10265`), not `townSearchOrder`. Toolkit’s town sweep searches around **home** (`:10144`). Copper-miss filtering applies only when copper was requested (`:11513`), not every coal-only draw. State these distinctions and identify exactly which queued change updates each caller; naming a metal home alone does not make toolkit open it first.

9. **P2 — §§1.1, 4.3, 6.1–6.3: the preview is not the specified planner.** `tools/homes.py.txt:11` includes every census container, independently chooses each group’s maximum, and neither resolves conflicts nor deduplicates doubles. `data/homes.json` assigns board-a’s wood home 43 blocks south, outside `inTown` (`chestfull.mjs:64`). “Containers needed sorted” is then presented as assigned homes. Run the actual canonical allocation over eligible containers and publish coordinates; distinguish census-box totals from usable town storage.

10. **P2 — §§1.5–1.6, 6.1: narrow the measurement claims.** `fit2.py.txt:48` excludes rectangles thinner than three cells, so it cannot establish absence of 5×2 workshops. Top-column reads do not prove supports, access or full construction feasibility. Run the actual predicates with positive fixtures and explicit candidate denominators. Label walk measurements as displacement estimates; they do not establish that travel is unimportant.

11. **P2 — §§7.2, 7.5, 11 O5–O6: causal recommendations exceed evidence.** The 31-block figure is an aggregate endpoint-distance statistic, not the starting distance of the 201 failures. Likewise, 1,306 unsuccessful drains are not proven outside-town targets. Measure start/target positions, failures and retained output by proposed eligibility before recommending either scope change.

12. **P2 — §9; O1: split and preregister the early canaries.** Planner/adoption, four placement paths, merge semantics, increased visit budget and far-deposit routing are not three small fixes. Stage counting, bootstrap placement and routing separately; isolate top-up and far routing. Forty deposits cannot validate all branches, and destination coordinates alone cannot measure prior contents or conservation.

1. **P1 — §§7.3, 8 T3: carry notes cannot establish what actually moved.** A crash after writing the note but before withdrawal can cause `tidy_return` to deposit the bot’s pre-existing iron.
