# ELK audit: what we store, what we read, and the 35 days we were throwing away

**2026-09-23.** Every number here is a live query against the cluster at 10.0.0.186, not a
reading of documentation. No assumptions.

## Access, and a correction to how it was described

- `mcai_ship` is **write-only** (role `mcai_writer`). It returns **403** on
  `indices:monitor/stats` — it cannot even list indices. Correct least-privilege design.
- The read account is `mcai_ro`, password at `/root/.mcai_ro_password` on the ELK host.
- **There was no Elasticsearch client anywhere in the repo.** `scripts/lib/telemetry.py`
  reads the JSONL FILES, and its own docstring calls Elasticsearch "the authoritative
  archive" for anything wider than a few days. 42.4M documents, nothing querying them.

## 1. Ingest is complete. This is a clean bill of health.

| | 24h |
|---|---:|
| JSONL rows written (live **and** rotated `.gz`, 1,208 files) | **920,654** |
| Documents in `mcai-skill-agents` | **920,671** |
| difference | **17 docs, 0.002%** |

Filebeat logged **zero** drop/reject lines in 24h. The `dynamic: strict` concern — that an
undeclared field silently rejects 100% of documents — is **not happening**. `bot.tools` is
declared. The pipeline is correct.

## 2. We have 50 days of data and have been analysing 15

| source | coverage |
|---|---|
| JSONL rotated generations | **15**: 09-02, then 09-10 → 09-23 — **with a gap** |
| Elasticsearch | **50 unbroken days**, 2026-08-05 → 2026-09-23 |

Total archive: **31,250,449** skill documents, **4,040,039** LLM, **7,128,002** journal =
**42.4M**.

Every "30-day review" this project has produced was computed over whatever the files still
held. The real series was in an index nothing queried. This is the single largest finding
of the audit.

**What it immediately buys**, from the first 50-day aggregation ever run:

| day | gather runs | ok% | dominant failure |
|---|---:|---:|---|
| 08-05 | 141 | 36.2% | **stuck 42%** |
| 08-10 | 3,178 | 13.8% | nothing_found 39% |
| 08-15 | 1,576 | 3.0% | no_safe_target 45% |
| 08-25 | 33,239 | 23.5% | nothing_found 23% |
| 09-01 | 26,786 | 10.5% | no_path 25% |

`stuck` was **42% of gather runs in early August and is now silent** — it appears in
today's silent-instrument list. It is not dead code; the fleet stopped entering that state.
`stagnation` likewise. That is the triage the silent-class question needed, and it is only
answerable with history the files no longer hold.

## 3. The Minecraft server logs have never been shipped

`mcai-mc-server` — **no such index**. The template exists (`apply-mappings.sh` creates
`mcai-mc-*`); the data stream was never created and nothing writes to it.

So the 16 Paper servers' own logs are absent from the archive. Concretely, the
`moved wrongly` warnings measured last night — 226 in one world in 2h20m, concentrated in
specific bots — exist only in `latest.log` on the worlds host, are wiped on restart, and
have no history at all.

## 4. `skill.fail_class` was queryable all along; `skill.detail` never was

- `skill.fail_class: keyword` — **mapped and aggregatable since the mappings were applied.**
  The typed vocabulary was available in ES the whole time, while the Python readers indexed
  only `skill.name` and 42 of 65 scripts fell back to regexing prose.
- `skill.detail: text` with **no `.keyword` subfield** — a terms aggregation on `detail` is
  impossible in ES too. So the field the analysis actually used is the one field that
  cannot be aggregated anywhere.

## 5. The LLM stream is 4M documents nobody has aggregated

`mcai-llm-agents` carries `llm.model`, `llm.latency_ms`, `llm.completion_tokens`,
`llm.prompt_eval_duration_ns`, `llm.eval_duration_ns`, `llm.load_duration_ns`,
`llm.endpoint`, `llm.admission`, `llm.error`, plus the full bot/exp context — 173,635
documents a day. Decision latency is 33–42% of fleet life by the project's own measure and
this is the instrument for it. No script reads it.

## 6. Two scripts default to a forbidden network

- `scripts/selfcheck.py:41` → `http://192.168.192.194:9200`
- `infra/observer/mcai-observer.py:29` → `192.168.193.30`

The owner's standing constraint is **do not use the 192.168.19x network**. These are stale
pointers at the retired instance #2. They should be repointed at 10.0.0.186 or deleted.

## What was built during the audit

- `scripts/lib/es.py` — read-only client. Raises on an ES `error` object rather than
  returning it as data, and never embeds a secret.
- `scripts/esaudit.py` — freshness, volume and mapped fields per stream.
- `scripts/eshistory.py` — real archive span and documents per day.
- `scripts/esfailtrend.py` — the 50-day failure-class series.

# AMENDMENT — an independent review found three of my claims wrong

**2026-09-23, after a second engine attacked this report.** The audit above was written by
one analyst with no second opinion, and the owner asked whether ChatGPT had seen it. It had
not. It has now, and it found real counterevidence. Corrections, each re-verified live:

## C-1. "The Minecraft server logs have never been shipped" — WRONG

I queried `mcai-mc-server`. **That index does not exist because it is not the name.** The
real stream is **`mcai-mc-paper`** — the Kibana data view in `infra/elk/kibana-objects.ndjson`
names it, and it holds **25,782 documents**.

The substance survives in a weaker and more useful form: `mcai-mc-paper` received **112
documents in 24h** and its newest document is **06:04Z against 13:48Z for the live streams**
— seven hours stale. Paper log shipping is nearly dead, not absent. 112 docs/day across 16
servers, against 920,902 skill documents.

**And enumerating instead of assuming found two streams I never looked at:**

| stream | newest document | 24h | total |
|---|---|---:|---:|
| mcai-mc-paper | 2026-09-23T06:04Z | 112 | 25,782 |
| **mcai-gpu-metrics** | **2026-08-15** | **0** | 22,067 |
| **mcai-supervisor-lab** | **2026-08-20** | **0** | 1,075 |

**Three dead or dying streams, not one missing one.** GPU metrics stopped 39 days ago and
supervisor-lab 34 days ago, and nothing noticed either.

## C-2. "There was no Elasticsearch client anywhere in the repo" — WRONG

`scripts/selfcheck.py:51` has an `es()` helper and queries `mcai-skill-agents/_search`.
`infra/guard/mcai-guard.py` queries `mcai-llm-agents` at lines 48, 59 and 100.

The accurate claim, verified across all three hosts: **neither is scheduled anywhere** — no
cron entry, no systemd unit, no output file. The code exists and nothing runs it. And
`selfcheck.py:41` defaults to `192.168.192.194`, on the network the owner forbids, so it
could not run as written.

## C-3. "Nothing reads the LLM stream" — WRONG

Besides `mcai-guard.py` above, `infra/elk/kibana-objects.ndjson` defines a seven-panel
dashboard, **"Fleet — cognition & decision quality"**, created 2026-08-06, covering veto
rate, decision volume, latency p50/p90/p99, structured-output validity, latency by endpoint,
prompt vs answer size, and decisions by code version. Its own description says the LLM index
"had 4,924 documents and zero panels. The veto rate climbed from 23% to 72% over 16 hours
with nothing showing it."

So the instrumentation for the largest known time sink was **designed, and the dashboard
definition is in the repo**. Whether it is loaded into Kibana today is a separate question I
did not settle.

## What survives unchanged

- **Ingest is complete.** 920,654 JSONL rows vs 920,671 ES docs in 24h, 0.002%. Re-tested
  for duplication: same-millisecond rows are *distinct* board entries, not retries (6 of 6
  distinct by content), so the small surplus is the window boundary.
- **50 days in ES vs 15 rotated generations with a gap in the files.**
- **`skill.detail` cannot be aggregated**, and this bit me inside the audit itself: a
  `match` on `avoid` returned **0** across 18,038 rows whose text I had just read verbatim,
  while `adopted` matched all 18,038. The analyzer drops the token and `_analyze` is 403 for
  the read account. I got the answer from the files instead: 309 avoid-gather mentions
  against log blocks across **10 of 80 bots** — contained, not fleet-wide.
- **Two scripts default to the forbidden 192.168.19x network.**

## The lesson worth keeping

Both of my wrong claims were **confident negatives from a name I chose rather than
enumerated** — the same failure this project keeps repeating, committed inside an audit
whose subject is that failure. `esaudit.py` now lists the cluster's streams instead of
hardcoding them.
