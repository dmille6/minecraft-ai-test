# Batching server for qwen3.5:9b on the 3090 (2026-10-31)

The owner approved this test 10-31 ~14:10Z, queued after the learning work. The question: can a batching server carry
qwen3.5:9b for the whole fleet on the fleet's own GPUs? Architecture qwen35 is a hybrid SSM with full attention on every
4th layer, and Ollama serves it one request at a time. The need is ~100-107 decisions/min. Gates: p50 <= 2.5 s,
p95 <= 5 s, >= 99% schema-valid.
Everything ran on the 3090 (10.0.0.16). The load generator ran on .31. The 5080 (10.0.0.72) was not touched or queried.
No bot, env file or queue entry was changed. Evidence and tooling are in `batching-3090-2026-10-31/` and
`scripts/host/batchload.mjs`.

## 0. Answer

- **Batching works for this architecture in the engine, but it buys little for this workload.** llama.cpp batches
  qwen35 properly. In `llama-batched-bench`, decode goes from 66 tok/s at B=1 to 637 tok/s at B=16. The fleet's
  decisions are prefill-bound, though: ~2,550 prompt tokens in, 43-62 out. Prefill runs at ~3,600 tok/s at any batch
  size, so batching only overlaps the cheap part.
- **On the 3090, no qwen3.5:9b configuration meets the gates at even 20 decisions/min.** The fleet needs 107.
  - Best case, llama-server with candidate 2 Q8: at 20/min open-loop, p50 3.1 s and p95 5.6 s. Its throughput
    ceiling is ~46/min.
  - Ollama on the same box, stock qwen3.5:9b: p50 13.3 s, p95 19.7 s at 20/min. It is serial, with a ceiling of
    ~20-23/min.
  - llama-server is ~1.6-2x Ollama, both serially and at the ceiling. That is still 2-5x short of the fleet.
  - Carryable within the gates is roughly **15/min, about 11 bots** (estimate between the c=1 run and the 20/min run).
- **The 3090 is a shared GPU.** ethan-gpu's llama-server was processing in **74% of 3,594 two-second samples**
  during the tests. Every number here was measured beside that load, and any 3090 serving plan would have to share
  with it permanently.
- **5080 (ESTIMATE, not measured).** It is probably **not enough for 107/min with qwen3.5:9b**. A plausible range is
  **~40-70/min within the gates (30-50 bots)** on llama-server (s.4).
- **Recommended setup:** llama.cpp `llama-server` b12020 with candidate 2 Q8 (or stock Q8), on a dedicated GPU (s.5).
  Before any move, measure it on the target card with `batchload.mjs` at the stage rate. The Blackwell is testing-only.
  The cheapest real lever is the prompt: once decode is batched, prefill is ~70-75% of the GPU time.
- **vLLM was not run.** No official pre-quantized Qwen3.5-9B exists (`Qwen/Qwen3.5-9B-FP8/-AWQ/-GPTQ-Int4` do not
  exist on HF). The bf16 weights (18-19 GB) do not fit in the 18.5 GB that ethan-gpu leaves free, nor on a 16 GB 5080.
  Disk on the 3090 was also 13 GB free at the start. A vLLM test needs a community quant, which the
  official-sources rule does not allow, or a bigger card.

## 1. What was installed (isolated, `~/batchtest` on the 3090, 1.1 GB left behind)

- llama.cpp **b12020** official release `llama-b12020-bin-ubuntu-cuda-12.8-x64.tar.gz` (175 MB, sha256 0170c61c...) plus
  `cudart-llama-b12020-bin-ubuntu-cuda-12.8-x64.tar.gz` (566 MB, a17d59ed...). Both are from GitHub ggml-org. The
  CUDA 13.4 build would need a newer driver than 595 (CUDA 13.2). libgomp was copied from Ollama's lib dir. Nothing was
  installed system-wide.
- Models were read through a **read-only bind mount** of Ollama's blob dir. The mount was removed at the end, and
  Ollama's files were not changed. Ollama's own `qwen3.5:9b` blob does not load in upstream llama.cpp
  (`qwen35.rope.dimension_sections has wrong array length; expected 4, got 3`: Ollama-format GGUF). So:
  - **stock Q4_K_M**: quantised for this test from the learning loop's upstream bf16 conversion of the base
    (`runs/base-qwen35-9b/qwen35-9b-base-bf16.gguf`). It came to 5.3 GB and was deleted afterwards.
  - **stock Q8_0**: `qwen35-9b-baseconv-q8` (learning loop's upstream conversion, 9.3 GB).
  - **candidate 2**: `cand-qwen35-9b-c2-q8` (9.3 GB).
- Server flags (`serve.sh.txt`): `-ngl 99 -fa on --jinja --reasoning off -np 8 --no-kv-unified -c 8x6144`, prompt
  cache on (default). The first candidate runs used `-np 32 --kv-unified -c 32x4096`. The server was restarted before
  every run, so no prompt was cached across runs.

## 2. Method

- `scripts/host/batchload.mjs` sends every request through the **fleet's own client** (`bots/src/llm.mjs`
  `LlmClient.decide`). That includes the schema grammar, the repair retry and the sentinel check, with the fleet env:
  ctx 8192, max 512 tokens, T 0.7, timeout 45 s.
  - For llama-server, a fetch wrapper maps the client's `/api/chat` call to `/v1/chat/completions`, with
    `response_format: json_schema` set to the bot's schema. "Valid" is the client's own verdict.
  - Two modes: open-loop Poisson arrivals at rate/min, and closed-loop N workers.
- Prompts: learnloop `m3-eval.jsonl`, 600 unique real logged decisions with rebuilt system prompts, schema and
  sentinel. Mean prompt is ~2,590 tokens. The live fleet last hour had 5,523 model rows, prompt p50 2,533 and p95 2,730.
  Both have 3 distinct system prompts, so the replay set matches today's shape.
- Ollama control: same client and prompts on the 3090's Ollama 0.32.14 (NUM_PARALLEL 2), with **think:false** added.
  This Ollama *thinks when think is unset*: 512 thinking tokens and empty content, i.e. 0 valid. The Blackwell's
  0.33.2 does not. Never point a bot at this Ollama for qwen3.5 without fixing that.
- GPU sampler every 2 s: VRAM per process, utilisation, and whether ethan-gpu's slot was processing (read-only
  `GET :1234/slots`).

## 3. Results (full table: `batching-3090-2026-10-31/table.md`)

"valid x/n" counts 45 s client timeouts as failures. Every answer that came back was schema-valid (100%). Above
capacity the failures are all timeouts.

| server / model | c=1 p50 | best throughput | open 20/min p50 / p95 | open 30/min p50 / p95 | VRAM |
|---|---|---|---|---|---|
| llama-server cand-c2 Q8 | 1.7 s (34.7/min) | **46.5/min** at c=4 | **3.1 / 5.6 s** | 6.4 / 11.1 s | 10.2 GB (np 8) |
| llama-server stock Q4_K_M | 1.8 s (32.0/min) | 37.4/min at c=8 | 5.5 / 11.7 s | 22.7 / 34.4 s | 7.0 GB |
| llama-server stock Q8_0 | 2.4 s (24.5/min) | 34.2/min at c=8 | 6.8 / 12.3 s | 20.4 / 30.8 s | 10.2 GB |
| Ollama qwen3.5:9b (Q4) | 3.2 s (19.1/min) | 22.8/min at c=4 | 13.3 / 19.7 s | 35.3 / 87 s, 11 timeouts | 6.6 GB |
| Ollama cand-c2 Q8 | 2.7 s (22.4/min) | ~31/min | 6.5 / 11.9 s | 17.5 / 24.8 s | 8.7 GB |
| Ollama qwen2.5:7b (calibration) | 1.8 s (33.4/min) | ~49/min | open 50/min: 9.6 / 16.6 s | open 92/min: 94 of 184 timed out | 5.5 GB |

- At 107/min every qwen3.5 configuration collapsed: 41-77 of 107 requests timed out.
- More slots make it worse past c=4-8 (cand: 46.5/min at c=4, 35.8 at c=16, timeouts at c=32). New prompts' prefill
  stalls the decode of every other slot. Server-side generation time for ~43 tokens rose from 0.56 s (c=1) to
  8.4 s (c=8).
- Candidate 2 is the fastest qwen3.5 because its answers are shorter: 43 vs 61-62 completion tokens.
- Prefix cache: the shared system prompt (~1,150-1,180 tokens) is reused on hybrid models too (`cache_n` 1,177 of
  2,487). Under concurrency the cached share drops from 0.42 to 0.20-0.37.
- Grammar is not the bottleneck: with the prompt cached, json_schema vs no grammar at 8 slots is 30-36 vs
  26-29 ms/token.
- **Engine vs server gap.** `llama-batched-bench` (cand Q8, 1,400 uncached + 45 out, i.e. with the system prefix
  cached) does 8 decisions in 4.3 s (~110/min) and 16 in 8.3 s (~116/min). llama-server reaches ~40% of that. The rest
  is lost to continuous batching that mixes prefill into decode steps, and to lower prefix reuse. A pure-attention
  control (Qwen3-8B Q8) scaled no better under the same load: 8 requests in 11-17 s. **So this is the workload and
  the server, not the SSM.**

## 4. 5080 estimate (ESTIMATE: not measured, nothing on .72 touched)

Calibration uses the same model, client and prompts on both cards, from the fleet's own logs only. qwen2.5:7b on the
5080 served the live fleet last hour at **~92/min with p50 1.70 s, p95 3.17 s** (5,215 rows). On this shared 3090,
Ollama qwen2.5:7b already fails the gates at 50/min (p50 9.6 s) and saturates at ~33-49/min. Within the gates, then,
the 5080 does **~3x** this 3090, from a dedicated GPU plus newer compute (spec: similar memory bandwidth, ~1.6x
tensor compute). Prefill-bound work follows compute.

Apply 2-4x to the 3090's qwen3.5 results. The within-gate rate on llama-server cand Q8 (~15-20/min) becomes
**~40-70/min (30-50 bots)**. The ceiling (~46/min) becomes ~90-180/min, but latency gates bind well before the
ceiling. **107/min with qwen3.5:9b on the 5080 alone is unlikely**, and the uncertainty is wide (2x either way).
VRAM: cand Q8 at np 8 x 6144 takes 10.2 GB and fits the 16 GB card alone. Beside qwen2.5:7b (6.5 GB) it does not, so
it would be a replacement, not an addition. Stock Q4 needs 7.0 GB.

## 5. Recommendation (control session's call, owner away)

1. **Do not plan a full-fleet qwen3.5:9b move onto the 5080 or the 3090 on this evidence.** Neither carries 107/min
   within the gates, by measurement (3090) and by estimate (5080).
2. If qwen3.5 serving on fleet GPUs goes ahead, use **llama.cpp llama-server b12020, cand-c2 Q8** (or stock Q8 if
   the candidate is not kept), with `-np 8 --no-kv-unified -c 49152 -fa on --jinja --reasoning off` and prompt cache on.
   This needs a client change: `llm.mjs` speaks `/api/chat` only. The mapping in `batchload.mjs` is ~20 lines. Size it
   as a partial-fleet canary (~20-30 bots on the 5080) and load-test the stage rate first with `batchload.mjs`.
3. **The biggest lever is prefill.** Prompt processing is ~45% of a decision's GPU time at c=1, and ~70-75% once decode is batched (bench B=8: 3.1 s prefill vs 1.2 s decode). Moving everything volatile to
   the end of the prompt raises the cached share. Trimming the ~1,400 uncached tokens raises capacity about in
   proportion. Either would help any server, including today's qwen2.5 on the 5080.
4. The 3090 is not a serving box while ethan-gpu runs there. It was busy 74% of the time.
