Written by the infrastructure agent while the operator slept. Findings are
recorded as they were established, including the ones where I was wrong.

agents' reasoning. An external review put it best partway through:

> Most "agent behavior" is probably infrastructure, synchronization, world
> physics, pathing, logging, or measurement error wearing a cognitive costume.

That was correct, and this document is largely evidence for it.

## The pattern worth keeping

**Capability without its inverse**, six or more times: something can be added but
never removed, a guard trips with no path forward, a counter increments where
nothing clears it. Blocks that could never be disproved. A watchdog that could
start bots but never checked whether it should. A reflex that could fire but not
stand down.

**Recovery mechanisms that outlived their world**, three times: the watchdog
restarting units on a host the bots had left; the homepage linking to a viewer
that had moved; a rescue point chosen for terrain since dug away. Each was
correct when written and became harmful when the system changed, and none had a
check that it still applied.

**A watchdog whose threshold sits inside the p90 of legitimate work will spend
most of its firings on false positives.** Fourth timeout-nesting bug here.

## Measurement, and why it was wrong

Excluding reflex noise: 409 real skill attempts, 107 "successes" — 26%. But
**144 of 313 successes (46%) moved zero blocks and changed no inventory**. Real
rate: 13.9%. Every success figure quoted before 2026-08-06 is inflated ~2×.

That is ADR-0003, and it was then reproduced as a controlled experiment. Swapping
to a faster 7B model:

```
                  14B/Studio   coder:7b/5080
admit-rate            71%           78%
median latency      3083ms        1793ms
productive skills   10 of 16      6 of 31
```

**Both headline metrics improved while the agent got materially worse.**

## What the agents actually have

A persistent brain, surviving death, respawn, restart and reconnect: per-bot
avoid/worked counts, hazard sites with coordinates, milestone give-ups, probation
counters. Plus a shared fleet store of hazards and abandoned goals, each tagged
with where it was abandoned — so "crafting a stick is impossible" applies only
within 64 blocks of where it was proven.

It was entirely negative. They remembered where they got hurt and what failed,
and nothing about where anything good was. Added tonight: shared resource
sightings, so a bot that walks past a forest records it for the fleet.

## The colony moved

The fleet had mined spawn into a crater — voids at y=69–75, no wood within 16
blocks, `gather` aborting 23 times in 45 minutes. Ground 24 blocks east is
intact. Forward base built at 28,79,0 (chests, crafting table, furnace), rescue
point and HOME follow it.

`HOME` had been `0,70,0` — **inside solid rock**. Every `home` call and every
livelock escape had been targeting a point in the cave layer.

## Where it stands

Bots harvested a tree at the new base and one crafted a **stick** — a goal the
fleet had collectively marked unreachable. Scout01 explored to 49,-20 unaided.
Remaining `gather` failures are honest: the leftover logs are floating canopy.

## What I got wrong

- Diagnosed "the 5080 is running on CPU" from a wrong premise about which host
  was which. `.70` is an M4 mini; 11.5 tok/s is normal for it.
- "Fixed" the homepage by editing a repo file the container does not mount, then
  verified by re-reading the file I had written.
- Built diagnostic probes four times that returned the same answer regardless of
  input — an RCON air-check, a `say`-based probe, an ES cardinality query, and an
  `npm view` against a machine with no npm.
- Called telemetry growth "blocked decisions becoming executed ones" when it was
  a broken reflex.
- Raised a heap ceiling twice instead of finding the cause.
- Nearly ran `fill ... replace chest` as a *query*.

The through-line: I verified by re-reading what I had just written, rather than
asking the system that consumes it.
