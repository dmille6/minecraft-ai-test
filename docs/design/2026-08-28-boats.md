# Boats — what the ecosystem knows, and what we would have to build

**Status: RESEARCHED, NOT BUILT.** Filed so it is not re-derived. Nothing here
ships until surface-only travel is measured; see the ordering argument at the
end, which the two reviewers disagreed on.

## Why we care

Drowning is the top killer and has been since day 1. Measured 2026-08-27, two
clean windows either side of a power outage:

|                 | hours | drown | episodes | per bot-h | per 1k episodes |
|-----------------|------:|------:|---------:|----------:|----------------:|
| pre-freeze      |  18.5 |    42 |    7,228 |    0.0284 |            5.81 |
| frozen A        |  15.5 |    52 |   13,995 |    0.0419 |     3.72 (0.64x)|
| frozen B        |   4.9 |    18 |    5,296 |    0.0464 |     3.40 (0.58x)|

Water episodes went 4.9 → 13.6 per bot-hour. Per-episode risk fell 42%;
absolute deaths rose 48-64%. Bots cross more and survive crossings better, but
not enough better to pay for crossing so much more.

A boat is ~8 m/s against 2.2 swimming, **and you cannot drown in one** — air
never depletes, so our corrupt `airScale` (a running max of a sensor that fish
contaminate, reading 20..400 across 222 distinct values) becomes irrelevant by
construction rather than by compensation. A boat costs 5 planks = 2 logs; bots
routinely carry 100-226 logs. Materially free.

`water-release.mjs` already treats "in a boat" as a durable safe state and
releases the drowning rescue on it. The architecture expected boats.

## THE ASSUMPTION THAT WAS WRONG

The obvious framing — "mineflayer-pathfinder has no boat movement, so we would
hand-steer by dead reckoning" — is wrong in a way that matters.

**`bot.moveVehicle()` is inert on boats.** It writes `player_input` /
`steer_vehicle`, which is *input only*:

```js
function moveVehicle (left, forward) {
  bot._client.write('player_input', { inputs: { forward: forward > 0, ... } })
}
```

Boats are **client-authoritative**. The server does not move them; the
controlling passenger's client simulates the boat and asserts its position via
serverbound `vehicle_move`. `grep -rn "vehicle_move" lib/` in mineflayer
returns **nothing** — it never sends that packet and never simulates boat
physics. So the paddle input goes to a server that was never going to move the
boat, which silently explains mineflayer #2766 (horse frozen while mounted),
#3615, #3726.

**Consequence:** once we send `vehicle_move` ourselves we are setting the
boat's position directly. Dead reckoning is not a fallback, it is the native
interface. There is no pathfinder to miss — open ocean has no obstacles and a
straight line is the correct path. The hard part is the failure detector, not
the route.

## Why nobody has done this — two boundaries, neither technical

**mineflayer refuses on policy.** Issue #2480: *"Boatfly gives an advantage
over vanilla players. Mineflayer tries to be as vanilla as possible."* The same
packet that drives a boat legitimately enables boatfly.

**Baritone refuses on architecture.** `FEATURES.md` has a section titled
"Things it may not ever have" and the list is exactly **Boats, Horses,
Elytra**. A* runs over discrete 1x2 player-sized moves; a boat is wider,
cannot jump, and carries momentum. 41 boat issues, all closed as duplicates.
The tell: when Baritone finally needed non-walking movement, **elytra shipped
as an entirely separate planner** (`baritone.process.elytra`, native octree
raycasts) sharing zero code with the movement graph.

**Research agents have never been in a boat.** Voyager's only boat is
`craftBirchBoat` — it crafts one and never rides it. JARVIS-1, Odyssey,
MineDojo, MineRL, Plan4MC and Project Sid have recipes and item strings only;
Sid has zero mount/vehicle code across 1000+ agents. Not one has crossed an
ocean. Citizens' `BoatTrait` is cosmetic. No cheat client has boat autopilot
either — Wurst's BoatFly reads the human's keys.

## The three implementations that exist

All independent, all one-person hobby repos, all reaching the same design.

- **`wehos/mc-agent-neko`** (MIT, 12 stars) — the closest analogue to us:
  `boatEscape` is wired **into a drowning reflex**, gated on oxygen and two
  non-solid blocks below. Its changelog says the gate was added after "2
  drownings + 3 shot/eaten in water" in one day.
- **`arielvino/ion-golem`** — `doSail()`, the cleanest minimal reference.
  `SPEED = 0.32` blocks/tick (~6.4 m/s), deliberately under the 8 m/s cap.
- **`voxta-ai/voxta-minecraft-companion`** — implemented the mechanism for
  horses and then explicitly `return`s on boats. Reason unrecorded, and it is
  the one negative data point nobody could explain.

## THE `NoPath` EQUIVALENT, which does exist

The objection was that dead reckoning gives no honest evidence about the world
the way a pathfinder failure does. It does.

**The server sends a CLIENTBOUND `vehicle_move` when it rejects an asserted
position.** Count them. Neko: if clamped >= 10 while still within 3 blocks of
origin, abort `'server clamped x10 at origin'`. That is a direct rejection
signal, strictly better than a distance timer, and it distinguishes "beached on
an island" from "anticheat is refusing me".

Both implementations also run displacement watchdogs — Neko aborts on net
horizontal displacement < 2 blocks over 20s; ion-golem on `movedTotal < 0.5` at
~3s and a stuck counter over ~20s.

## Mechanics we would have to handle

- speeds: water **8 m/s**, ice 40, blue ice 72.7, land 2
- **land collision has NOT broken boats since alpha** — beaching is safe
- destroyed above 40 accumulated damage; weapons over 4 hearts one-shot it
- mobs board boats and **keep attacking from inside** — a drowned climbing in
- Java boats cannot travel upstream to higher elevations
- dismount already attempts to place the player on land
- recovery is hitting it until it drops; Neko gives up after 6 swings with
  "the boat is 5 planks, life is worth more"
- **server speed check**: exceeding it logs "Vehicle X of Player Y moved too
  quickly!" and rubber-bands. Both implementations chose 0.32-0.34 b/tick for
  headroom. A 1000-block straight line at constant speed with zero jitter is
  not a shape a human produces; third-party anticheat will be stricter.
- **boat placement may be broken**: Neko reports `bot.placeEntity` fails for
  boats on 1.21.1 because `place_entity.js` writes `use_item` without
  `sequence`/`rotation`, and nmp serialization errors surface asynchronously so
  nothing throws at the call site. Their fix was `bot.activateItem()`.
  UNVERIFIED against current mineflayer.

## THE HAZARD THAT WOULD BE OURS

**Dismount freeze.** Neko flags it hardest: if dismount fails,
`shouldUsePhysics` stays `false` and the bot **stays frozen in the boat**. They
retry 3x at 1.5s and still log a warning.

That is exactly the trade to be careful of — boats convert a lethal problem
into an ENTRAPMENT problem. A bot in a boat in open ocean is perfectly safe and
may go nowhere forever, invisible to every death-based tripwire we have. This
project is already dominated by entrapment: 61% of the fleet hits no-route
underground, `home` succeeds 5.1%.

**So the rule, and it is not optional: "in a boat" means SAFE, never
SUCCESSFUL.** Success requires arrival within a shore radius, or a real
reduction in distance-to-target handed off to land pathing. Failure gets
first-class events — `boat_stuck`, `boat_no_progress`, `boat_lost`,
`boat_ejected`, `boat_arrived_no_land_path`, `boat_timeout` — shipped WITH the
skill, not after. If success metrics count "not dead" as good, boats will look
falsely excellent.

## Ordering — the reviewers disagreed

**ChatGPT: boats first, scoped.** Two swim changes have now made drowning worse
per bot-hour; another swim change carries a poor prior. Boats remove the sensor
dependency structurally instead of compensating for it. Its policy: crossing
> 80-120 blocks → boat; already in water and home > 150 blocks → boat; no
materials and short distance → surface swim.

**Claude: surface-only swimming first.** It is a change to one branch using
observables that already exist (`headIsAir`, `canSurface` are computed today
and simply not used for control). Boats are a new skill with a dozen new
failure modes, and this project's history with new water skills is `swim_to`
shipping once and TRIPLING drowning.

Unresolved. Decide deliberately rather than by whichever gets started.

## Before any fleet code

**Bare-client repro** (playbook pattern 10). The client-authority claim is
convergent across the 1.21.4 protocol spec, mineflayer's source, three
codebases and Wurst — but nobody in this investigation ran a server or sent a
packet. One plain mineflayer bot, one boat, one `vehicle_move`, on our own
Paper build, before anything else. Also read the real `moved too quickly`
threshold out of that build rather than trusting a secondary source.
